## 核心约束（决定了整个做法）

**Ollama API 只有 5 小时会话窗口和每周窗口累计，根本没有「天」维度。**

所以现在插件里所有"按天"的数字（趋势表的「当日」列，commit `9087e16`）
都是靠**相邻两日日终值差分**还原出来的，不是 API 给的。

**周窗口边界是实测出来的**：`week` 字段是周一日期，**周一 08:00 重置**
（上周 `week=2026-09-21` 在 9/28 变成 `2026-09-28`）。

**快照字段只有 7 个**（`$DSH_HOME/ollama-quota-history.json`）：

```
t · date · week · sessionPct · weeklyPct · sessionReqs · weeklyReqs
```

## 「每天可用量」的三种含义

做出来完全不同，动手前必须选一个：

| 方案 | 含义 | 显示成 |
|---|---|---|
| **A. 均分预算** | 剩余% ÷ 剩余天数 | 「今天有 15.26% 的预算」 |
| **B. 今日剩余** | 预算 − 今天已用 | 「今天还能用 6.6%」 |
| **C. 速率预警** | 按当前速率何时耗尽 | 「照这速度周四见底」 |

**当时的建议是 A + B 一起做，C 作为可选告警。**
A 单独做意义不大 —— 用户看到「15.26%」也不知道自己今天用超没有。

## 四个没定下来的问题

1. **单位** —— 百分比 / 请求数 / 两个都显示？
   - 当时的倾向：**以百分比为准，请求数只作参考**
   - 理由：`1% ≈ N 请求` 的比值**不稳定**，不同模型差很多
2. **「天」怎么切** —— 自然日 `00:00–24:00`（与落盘的 `date` 字段一致，当时推荐）
   还是跟窗口对齐 `08:00–08:00`？
3. **放哪儿** —— 📈 趋势表**加一列**，还是**标题栏常显**一个小指示
   （如 `今日 13.4% / 预算 15.7%`）？
4. **要不要告警** —— 超预算时提醒（iMessage / 会话内），还是**看得到就行**？
   - 若要做，还得定**提醒频率** —— 每次查询都提醒会烦死人

---

## ⚠️ 当时就提醒过的坑：均分预算一定会被"打脸"

**实测：一周里前松后紧，消费极度不均衡。**

```
9/21 周一   2.1%   ← 几乎没动
9/22        8.0%
9/23       10.3%
9/24       25.9%   ← 开始发力
9/25       45.2%
9/26       53.7%
9/27 周日   66.6%
```

所以「每天 15.26%」在**周初毫无约束力**（才用 2%），到**周四会突然报警**（已用掉一半）。

**它是「平均参考线」，不是「硬上限」。** 这点必须先和用户对齐，
否则他会觉得这个功能总在误报 —— **这很可能正是「暂缓」的原因之一。**

## 如果将来要捡起来

**最小实现**（假设采用 A + B、自然日、标题栏、不做告警）：

1. `index.js` 里已有快照读写；新增一个 `computeDailyAllowance()`：
   - 取最新 `weeklyPct` → 剩余% = `100 - weeklyPct`
   - 算剩余天数（到下一个周一 08:00）
   - 均分预算 = 剩余% / 剩余天数
   - 今日已用 = 今日 `weeklyPct` − 昨日日终 `weeklyPct`
   - 今日剩余 = 均分预算 − 今日已用
2. `client.js` 标题栏加一个小指示，复用现有快照数据，**无需新的 API 调用**
3. 无需改快照格式 —— **现有 7 个字段够用**

**唯一要新增的判断**：如何处理「周窗口刚重置、还没有昨日日终值」的边界
（此时今日已用无法差分，只能显示预算、不显示余额）。
